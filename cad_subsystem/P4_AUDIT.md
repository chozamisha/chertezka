## 1. INP-009 — принятый припуск vs TABLE6_BASE

### Откуда берётся `TABLE6_BASE = 5.2`

Цепочка (P1, без изменения формул):

1. Вход: `general_tolerance_mm=2.8`, `finish="Чистовая"`, `allowance_row=11` (`wheel_inputs.py`, лист расчёта §1).
2. Lookup: `allowance_mm(2.8, "Чистовая", 11)` → `gost_26645_table6_full.json`.
3. Строка допуска: **«Св. 2,40 до 2,80»**; значение ряда 11 для чистовой = **5.2**.
4. Provenance: `TABLE6_BASE` kind=`calculated`, unit=`mm`, detail=`allowance_mm(2.8, 'Чистовая', 11)`, doc_ref=`ГОСТ 26645-85 табл.6`.

В vendored JSON поле `meaning`: *«Общий припуск на сторону, мм, не более, для ряда припуска отливки 1..18»*; unit = mm. Аудит не переинтерпретирует ГОСТ сверх этой фиксации в knowledge.

### Что сравнивается с `TABLE6_BASE`

В `pipeline.py` для **каждого** из `N_TOP`, `N_BOT`, `N_FACE`, `N_HUB_OD`, `N_BORE`, `N_BOSS` пишется provenance, но **предупреждение** выдаётся только если:

```text
name ∈ {N_TOP, N_BOT, N_FACE}  ∧  val < TABLE6_BASE
```

Для КП-062215009-01:

| Параметр | Значение | vs 5.2 | Результат pipeline |
|----------|----------|--------|--------------------|
| N_TOP | 6.0 | ≥ | без warning |
| N_BOT | 5.0 | < | warning |
| N_FACE | 5.0 | < | warning |
| N_HUB_OD / N_BORE / N_BOSS | 4 / 4 / 3 | не сравниваются с base | — |

**INP-009** не считает заново: он поднимает **все** `calc.warnings` в один WARNING. На этом прогоне warnings ровно два и оба про N_BOT/N_FACE — совпадение с деталью отчёта. Если позже появятся другие pipeline-warnings, они попадут в тот же ID без разделения.

### Смысл сравнения и ГОСТ 26645-85 табл.6

- Сравниваются **линейные припуски на сторону (мм)** с табличным «общим припуском на сторону (мм)» — единицы и размерность согласованы.
- Физический смысл параметров разный: `N_TOP` — верх ступицы (верх формы), `N_BOT` — низ диска (низ формы), `N_FACE` — торцы дисков (толщина). Это **не** диаметральные припуски `N_HUB_OD` / `N_BORE` / `N_BOSS`.
- Pipeline трактует `TABLE6_BASE` как **базу для контроля снизу** (`N < base` → warning). Лист расчёта явно: *«табл.6 = 5,2 → округление/верх формы»*; N_TOP=6 (вверх), N_BOT/N_FACE=5 (округление / низ).
- **Напряжение формулировок (без выдумывания нормы):** в JSON meaning есть «не более». Pipeline/P1 при этом предупреждают о значении **меньше** таблицы. Аудит **не** объявляет, какая интерпретация нормативна: для смены статуса на FAIL/PASS нужно сверка с текстом ГОСТ 26645-85 (название/примечания табл.6) инженером, не автоматическая подмена.

Обозначения/единицы **не перепутаны**: mm ↔ mm; имена N_* соответствуют поверхностям в `calc.md` и формулам `C_H_HUB = H_HUB+N_TOP`, `C_T_* = T_DISK+N_FACE`.

### Почему WARNING, а не FAIL или PASS

- Значения **не** подменяются на 5.2 (P1: engineer + лист расчёта).
- Отклонение зафиксировано и требует внимания, но не стопит генерацию — осознанный soft-контроль.
- PASS был бы ложным: факт `N_BOT/N_FACE < 5.2` есть.
- FAIL без отдельного инженерного решения противоречил бы принятому листу расчёта и политике «не менять расчёт без обоснования».

**Вердикт аудита INP-009:** статус WARNING уместен как сигнал; сравнение касается N_BOT и N_FACE (не «оба и только они» в коде — ещё и N_TOP, который здесь проходит); нормативное направление «≥ base» vs формулировка «не более» в JSON — открытый вопрос к тексту ГОСТ, не к багу единиц.

## 3. DRW-016 — привязка DIMENSION ↔ геометрия OCP

### Что есть на чертеже (10× `DimLinear`)

Только тип `DimLinear` (`p1`, `p2`, `offset`, `text`) — **нет** поля association / edge_id / feature.

| 60 | L_PRINT | Б-Б местный | 30.0 | зависит от transform местного вида |

Уже доступная геометрия OCP для **частичной** сверки (без нового нормативного изобретения):

- bbox А-А width ≈ C_OUT (уже в GEO-005 / `assert_wheel_views_ok`);
- высоты тела/прибыли из сборки / CastingSpec;
- габарит местного Б-Б знака (L_PRINT + rim) — частично в `assert_wheel_views_ok`.

### Что пока не поддерживается

- ассоциация размер ↔ конкретное ребро/дуга BRep;
- отдельные сущности DimDiameter / DimRadius / DimAngular (диаметры сейчас — линейные с префиксом ⌀);
- размеры только на выносках (Leader) без DimLinear;
- семантическая привязка «этот размер на плане = тот же feature, что на А-А».

### Как реализовать проверку без ложного PASS

1. Разбить DRW-016 на подпункты (или один агрегат с худшим статусом).
2. Для каждого DimLinear:
   - распарсить число из `text`;
   - сопоставить с полем CastingSpec **только** при явной карте feature→param (иначе NOT_CHECKED, не PASS);
   - опционально: `|span · view_scale − value| ≤ tol` → PASS/FAIL по согласованности аннотации с геометрией листа;
   - сверка с OCP: только если есть измерение того же feature (bbox/секция/длина знака), иначе NOT_CHECKED.
3. Итог DRW-016 = PASS **только** если все размеры на листе закрыты; любой без привязки → NOT_CHECKED (как сейчас для всего блока) или FAIL при явном противоречии.
4. **Не** ставить PASS за «текст ⌀825 есть в blob» (это зона DRW-005) и не за «число DimLinear ≥ N».

**Вердикт:** текущий NOT_CHECKED для DRW-016 — правильный; частичная реализация возможна для линейных габаритов/диаметров из CastingSpec+масштаба вида, но полный PASS сейчас был бы ложным.

## 5. `fully_verified` и статусы

Реализация (`status.py`):

```text
fully_verified ⇔ ¬has_fail ∧ ¬has_not_checked
```

Проверено на отчёте колеса:

| Условие | Факт | Влияние на fully_verified |
|---------|------|---------------------------|
| FAIL | 0 | не блокирует |
| NOT_CHECKED | 1 (DRW-016) | **блокирует** → False |
| WARNING | 4 | **не** блокирует (и не считается PASS) |
| NOT_CHECKED == PASS? | нет | отдельный статус и отдельный счётчик |

Соответствие ТЗ P4: NOT_CHECKED не объявляется PASS; при наличии NOT_CHECKED чертёж не «полностью проверен». WARNING остаются видимыми замечаниями при возможном будущем `fully_verified=True` (когда DRW-016 будет закрыт) — это согласовано с формулой, но инженеру важно не читать «fully_verified» как «нет замечаний».

`is_passing` в смысле «нет FAIL» на колесе выполняется; `fully_verified` — нет. Отчёт markdown явно пишет про NOT_CHECKED.
